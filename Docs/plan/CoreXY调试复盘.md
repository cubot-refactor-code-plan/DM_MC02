# CoreXY 模块层调试复盘

> 时间：2026-10-22 ~ 2026-10-23
> 对象：`User/Module/corexy.*`、`User/Module/module_cfg.*`、`User/App/task/corexy_*.cpp`、`User/Device/device_emmv5_group.*`
> 结论：**单轴 / 45° / 分段双电机运动均已实机走通**，以下问题全部定位到根因并修复。

```

```

## 2. 问题清单

按“现象 → 根因 → 修复”排列，序号大致是踩坑顺序。

### P1 上电后电机高速跑飞、撞限位

- **现象**：发一条位置命令，电机不停机地往一个方向冲，只能断电。
- **根因**：用**绝对模式**下发负目标。协议里 `clk` 是 32 位无符号，`-1600` 被写成
  `0xFFFFFEC0`（≈ 42.9 亿脉冲），驱动器老老实实按这个数走。
- **修复**：统一改成「相对模式 `raF=0` + 方向字节 `dir` + 正幅值 `|clk|`」。
  类内再也不向协议写负数。
- **教训**：协议里凡是无符号字段，符号一律走单独的标志字节。DMA 一发出就无法收回，
  这类错误在台架上就是撞机。

### P2 命令返回 OK，但电机一动不动

- **现象**：`m x y` 打印发送成功，位置不变，最后 `FAULT TIMEOUT`。
- **根因**：相对模式是“以**上一次输入的目标**为基准”叠加的。故障 / `stop()` / 手动推过之后，
  软件书签（`_cmd_target`）与实际位置脱节，算出来的增量是 0 或错值。
- **修复**：每段增量一律用**实测 counts** 反算当前脉冲作为基准：
  `now_pulse = round(_cur_counts / _counts_per_pulse)`，`delta = end_pulse - now_pulse`。
  书签值只用于**到位判定**，不再参与增量计算。
- **教训**：闭环系统的“已知目标值”永远不可信，只有反馈可信。

### P3 `FAULT TIMEOUT`：电机没使能

- **现象**：命令发了，位置不动，超时。
- **根因**：驱动器上电默认不使能；早期版本还留着一个每 500 ms 关电机的 `zdt_task`，
  把两台电机反复关掉。
- **修复**：删除 `zdt_task`；`corexy_io_task` 启动阶段做 `zero → en 1 → en 2 → 复核读数`。
- **教训**：驱动器状态是外部状态，软件必须显式建立并验证，不能假设。

### P4 45° 段永远判不到“到位”

- **现象**：对角段走完却一直 `Moving`，直到超时。
- **根因**：45° 段只有一台电机参与，另一台不发命令。到位判据要求“`_fresh` 来自**命令过**的
  那台”，于是不动的那台把整段卡死。
- **修复**：判据改成「**两台都必须有本段的新读数**（`_fresh[0] && _fresh[1]`）且都落在窗口内」。
  不动的电机也要被轮询，它的“停在原地”本身就是有效信息。
- **教训**：多轴同步里，“没动的轴”同样需要证据；否则一台掉线也能判通过。

### P5 连续发两帧，驱动器只认第一帧

- **现象**：先发停止、再发使能，使能经常不生效。
- **根因**：`Uart::send()` 只是**入队**到 stream buffer，DMA 会把两帧首尾相接发出去；
  驱动器按 `0x6B` 切帧，遇到粘连的字节流就会错位。
- **修复**：`zero` / `enable` / `stop` 这类连续帧之间插 `SEND_GAP_MS = 5 ms` 的真实延时
  （115200 下 13 字节约 1.1 ms，5 ms 足够让驱动器解析完）；使能帧间隔放宽到 20 ms。
- **教训**：串口“发送成功”≠“对方收到了完整帧”。异步发送必须按线上时间留间隔。

### P6 一条 MMCL 带两台子命令，两台都不执行（本次最难点）

- **现象**：`0 0 → 50 60` 的第一段（45°，单子命令）能走；第二段（两台，双子命令）
  **完全不执行**，2 s 后 `FAULT TIMEOUT`，位置停在中转点。
- **排查过程**：
  1. 加 `dump` 命令打印实际发出的字节，与张大头官方实现 `Emm_V5_Multi_Motor_Cmd()`
     逐字节比对 —— 组帧**完全正确**：
     `len = payload + 5`，子命令自带 `0x6B`，帧尾再补一个 `0x6B`；
  2. 于是问题不在协议，而在**总线时序**：`update()` 里“请求 `0x36`”排在“到位判定”之前，
     到位那一拍先发了 `01 36 6B`，**0 ms 之后**又发 MMCL；
  3. 驱动器 0.26 ms 后开始回 8 字节应答，而我们 2.7 ms 的 MMCL 正在总线上发 ——
     半双工下收发撞车，驱动器自己发送时收不进字节，整帧被丢弃。
  4. 第一段是从命令队列发的，恰好没赶上同一拍的查询，所以能执行 —— 完美解释了
     “第一段能走、第二段不走”。
- **修复**：发位置命令前 **静默 `SEND_QUIET_MS = 20 ms`**，静默期内同时置 `_poll_hold`，
  保证一条查询都不发；发完再 `_poll_hold = 30 ms` 给驱动器处理时间。
- **教训**：
  - “命令没执行”先怀疑**线上有没有真正收到完整帧**，不要先怀疑协议字段；
  - 半双工总线上，“发查询”和“发命令”必须互斥且留间隔；
  - 现象的不对称性（第一段行、第二段不行）是定位时序问题的强线索。

### P7 第二段提前下发 → 两轴失步 → 撞限位（`m 1 1` 必现）

- **现象**：从 `(123,21)` 走到 `(1,1)`，第一段走一半就 `FAULT BAD_ARG at +87.45 -0.30`。
- **定位**：反解故障时刻的电机脉冲：

  | | 第一段目标 | 故障时实际 |
  | --- | --- | --- |
  | p1 | -8299 | -6971（多走 1328） |
  | p2 | 8172 | 7020（走了 1152） |

  两台都进了**第二段**约 15%；y 从 1.0 掉到 -0.30，越出理论限位 → 被拦停。
- **根因**：到位容差 0.20 mm = 16 个脉冲，60 RPM 下约 5 ms；而轮询 10 ms 一次，
  **完全可能在减速段末尾**就采到“已在窗口内”。此时驱动器还没停稳，紧接着下达的相对
  位置命令叠加在未完成的运动上，两轴立刻失步。
- **修复**：到位判据加**连续确认** `ARRIVE_CONFIRM = 2` 拍（约 40 ms），
  `stop()` / `_send_segment()` / `zero_here()` 都复位该计数。
- **教训**：闭环“到位”要有**时间维度**的确认，单次采样只能证明“此刻看起来在附近”。

### P8 贴边走时被理论限位误杀

- **现象**：`y` 目标只有 1 mm，正常减速过冲 1 mm 就判 `BAD_ARG`。
- **根因**：理论限位包围盒的外扩容差沿用了 `arrive_tol`（0.2 mm），比正常跟随误差还小。
- **修复**：包围盒容差改用 `OVERRUN_MM`（3 mm）。真正的跑飞由
  「轴级 `_seg_travel ± OVERRUN_MM`」+「理论矩形 ± 3 mm」两层拦住，灵敏度足够。
- **教训**：保护层的阈值必须大于**正常工况的波动**，否则会把正常工况当故障。

### P9 多任务访问同一条半双工总线

- **问题**：`multi_clear / queue_* / multi_send` 是三个独立调用，中间可能被别的任务插帧；
  单帧发送也没有互斥。
- **修复**：设备组新增**递归互斥锁** `_bus_lock`（`lock_bus()` / `unlock_bus()`）：

  | 位置 | 保护范围 |
  | --- | --- |
  | `_send_for()` | 单帧发送 |
  | `stop_all()` | 广播停止 |
  | `multi_clear()` / `_queue_for()` / `multi_send()` | MMCL 缓冲与整帧发送 |
  | `CorexyT::_send_segment()` | 静默期 + 组帧 + 发送（整段事务） |
  | `CorexyT::_stop_motors()` | 逐台 + 广播三帧 |

  用递归锁是因为调用天然嵌套（`_send_segment → multi_send → 内部再取锁`）。
- **注意**：锁解决的是**并发插入**，解决不了 P6 的**同任务内背靠背**，静默期仍必须保留。

### P10 同一个 P6 又犯了一次：只有「运动段」加了静默

- **现象**：`en 0` 后**只有电机 1 失能**，电机 2 仍抱死；随后所有移动都
  `FAULT TIMEOUT`——位置明明到了目标（`pos=(90.05, 70.05)`）却一直判不到到位，
  长行程（>100 mm）尤其明显。
- **根因**：P6 修的是 `_send_segment()` 里的发帧前静默，但**使能 / 失能 / 清零 / 停止 /
  直发 `0xF1`·`0xFC` 这些入口没有静默**。它们都是“无应答命令”，一旦碰上驱动器正在回
  `0x36` 应答，帧就被丢掉：
  - 失能丢一帧 → 只有一台失能；
  - 清零丢一帧 → 编码器零位与软件原点差一个常数，而到位判定用的是
    「绝对坐标 × counts/脉冲」，于是**永远对不上**，直到段超时 → `TIMEOUT`。
- **修复**（两处，缺一不可）：
  1. 模块层新增 `_quiet()` / `quiet()`，`enable()`、`zero_here()`、`_stop_motors()`、
     `_send_segment()` **统一** 走「总线锁 → 静默 20 ms（同步挂起轮询）→ 发帧」；
     上层直发诊断帧前调 `corexy.quiet()`；两台使能之间留 `ENABLE_GAP_MS = 20 ms`。
  2. 到位目标改成 **`段起点实测 counts + 本段增量 counts`**（增量式），不再依赖
     「编码器零位 == 软件原点」。零位有偏差时只影响世界坐标读数，不影响每段能否停住。
  另：`_seg_timeout` 补上减速时间（`run + 2·ramp`），长行程不再被误判超时。
- **教训**：
  - 静默期是**总线级不变量**，不是“发位置帧时的特殊处理”。凡是 `send()` 前，都要问
    一句「对面现在是不是在回我上一个问题」；
  - 无应答命令出了问题**没有任何反馈**，只能靠“动作没发生”反推，所以宁多停 20 ms；
  - 判定条件尽量不要引用**外部基准**（编码器零位），能用增量就不要用绝对。

### P11 分段移动时第二段只有一台电机先执行（用户给出总线时序，已按此定稿）

- **现象**：`m 100 50` / `m 1 1` 这类要拆段的目标，第二段的两个子命令在**同一个 MMCL 帧**里，
  但电机 2 立刻执行、电机 1 晚几百毫秒~1 秒才补上。中途 `pos` 会看到 `(75,25)` 这种
  “只有一台走完了第二段”的中间态（`c1` 还停在第一段终点，`c2` 已经到第二段终点）。
- **根因**：第二段 MMCL 在电机 1 上一段**还没真正停稳**时就发了。驱动器把新的相对位置命令
  当成“下一条目标”排队，等上一段跑完才执行 → 同一个 MMCL 里两台不同时动。
  对到位判断的误导：`0x36` 读回的位置只要进 0.2 mm 窗口就算“到位”，而减速尾巴还有几十毫秒。
- **用户给的正确时序（硬性约束，不要改）**：

```text
1. 发 MMCL（1 条或 2 条子命令；两台一起发，不拆帧）
2. 间隔 5 ms —— 发完之后不能紧跟着 read
3. read 1：发 0x36 → 等它回应答
4. 间隔 5 ms
5. read 2：发 0x36 → 等它回应答
6. 两个 read 返回的位置都“正确”（|反馈 - 本段目标| ≤ arrive_tol）才继续
7. 再间隔 5 ms，发下一条 MMCL，回到第 2 步
```

  - 半双工总线：一次只能有一条查询在途，必须“一问一答”；两条查询之间也要间隔。
  - **不允许用驱动器的“到位帧”（`FD 9F`）判到位**：那个回报默认不开，只看 `0x36` 读回的位置。
  - 不动的电机（45° 段只有一台动）也要 read，它的“停在原地”同样是本段执行成功的证据。
  - 单段超时给**非常大**（`SEG_TIMEOUT_MS = 300 s`），宁可等也不要把正常运动判成 `TIMEOUT`。
- **实现**（`User/Module/corexy.*`）：
  - `_read_position()`：发 `0x36` → 最多等 `REPLY_TIMEOUT_MS`（10 ms）收应答，一问一答；
  - `update()`：`_read_hold` 到点后读 1 → 隔 `SEND_GAP_MS` → 读 2，`read_ok = 两台都读到`；
  - `arrived = read_ok && 两轴都在窗口内`，连续 `ARRIVE_CONFIRM`（=2）拍；
  - `_send_segment()` 发完 MMCL 把 `_read_hold` 推到 `+READ_GAP_MS`（5 ms）；
  - 删掉了交替轮询 / `_fresh` / `_settled` / 段间减速停顿这一套。
- **教训**：
  - “同一个 MMCL 帧”只保证**同时下发**，不保证**同时执行**；执行顺序取决于每台驱动器当时的状态；
  - 到位判据必须要拿到**本拍两台的真实读数**，不能靠“曾经收到过”的累积标志；
  - 总线时序是硬约束（发完命令 5 ms 内不许 read、一问一答），不要用“多等一会儿”代替。

## 3. 可迁移的经验

1. **先证伪“字节有没有发出去”**，再怀疑协议。`dump`（打印实际帧）+ 官方参考实现逐字节比对，
   两次都比字段设计更有效。
2. **不对称现象优先怀疑时序**：一段成一段败、一台上台不上，几乎都是“时间/顺序”问题。
3. **协议里的有/无符号是硬约束**：负数绝不能塞进无符号字段，符号走独立标志字节。
4. **反馈优先于书签**：相对运动的基准必须是实测值。
5. **到位 / 到点判定要加时间确认**，单采样不可靠。
6. **保护阈值 > 正常波动**，并且要有“粗保护 + 细保护”两层。
7. **调试命令值得先写**：`pos / t / a / v / st / mode / clr / halt / dump` 让现场定位从
   “猜”变成“看”。这套命令最后保留在 `corexy_io_task` 里。

## 4. 现场验证流程（推荐顺序）

> 2026-10-23 之后控制台默认走 ASCII 命令码终端（`corexy_console_task`），
> 二进制协议用 `app_task.hpp` 的 `APP_COREXY_PROTOCOL` 打开（见 `corexy.md` §6、
> `User/Protocol/corexy_protocol.md`）。下面的命令清单与终端一致。


```
stop.            # 清故障
en 1.            # 使能（两台都发）
pos.             # 确认 f1=1 f2=1（两台都在回读数）、z=ok（原点已复核）
spd 300 230.     # 速度
j 10.            # 单轴试水：+X 10 mm
t 1 100.         # 单电机 +100 脉冲，核对单台接线/方向
m 50 50.         # 45°：只应电机 1 转
m 50 60.         # 分段：先 45° 再轴向，第二段两台都动
dump.            # 打印最近一条 MMCL 总帧，核对字节
```

判据：`done` 且 `pos` 与 `tgt` 相差在 `arrive_tol` 内；`c1 / c2` 稳定不漂。

## 5. 剩余风险 / 后续可做

- **没有真正的插补**：分段只走 45° / 90°，短段之间会有一个减速—再加速的停顿
  （约 40~60 ms）。对节拍要求高的场合需要轨迹规划层。
- **`rpm_i` 按脉冲比例分摊**只是“同时到达”的近似，加减速段两台仍可能有几 ms 的不同步。
- **驱动器 MMCL 的 `0xAA` 属于 Y42 组合指令特性**，换驱动器时要重新确认支持性。
- **堵转保护**未纳入状态机：`0x3A` 的堵转位目前只做诊断打印，未自动进 `Fault`。
