# CUBOT 编码风格规范

> 适用范围：`User/` 下的全部代码；基准样板为 `User/Bsp/bsp_uart.{hpp,cpp}`。
> 格式类规则已固化在 `.clang-format`（手动执行格式化）；命名、注释、架构类规则需人工遵守。

---

## 1. 文件组织

| 规则 | 说明 |
|---|---|
| 文件名 | 全小写 + 下划线：`bsp_uart.hpp`、`can_bus.cpp` |
| C++ 头后缀 | `.hpp` |
| C++ 源后缀 | `.cpp` |
| 头文件保护 | `#ifndef __XXX_HPP__` + `#define` + 末尾 `#endif // __XXX_HPP__` |
| 间接包含的头文件 | 行尾加 `// IWYU pragma: keep`，规避 clangd 误报（详见 [../guide/clangd配置.md](../guide/clangd配置.md)） |

C 调 C++ 的转接头见第 7 节，文件说明块的位置见第 3 节。

## 2. 命名规范

| 元素 | 规则 | 示例 |
|---|---|---|
| 类名 / 结构体 / 枚举类型 / 类型别名 | 大驼峰，不加 `_t` 后缀 | `PidConfig`、`PidInput`、`ImuData` |
| 方法 / 自由函数 / 类的全局实例 | 小写蛇形 | `init()`、`start_reception()`、`bsp_init()`、`calc()` |
| 私有成员变量 / 私有函数 | `_` 前缀 + 小写蛇形 | `_huart`、`_rx_stream_buffer`、`_diff_mode` |
| 宏 / 常量 / 枚举值 / 模板参数 | 全大写蛇形 | `MAX_INSTANCES`、`DATA_PACK_MAX_LENGTH` |

例外：

1. 构造函数 / 析构函数必须与类名（大驼峰）一致，如 `BspUart::BspUart()`
2. 外部库（HAL / FreeRTOS / 其他 C 库）强制要求固定名称的回调，如 `HAL_FDCAN_RxFifo0Callback`、`HAL_UART_RxCpltCallback`、`__io_putchar`、`_write`
3. CubeMX 生成的默认任务名（如 `StartDefaultTask`）保留原名，以便 CubeMX 重新生成时同名兼容

## 3. 注释规范（Doxygen）

> **@file 说明块只写在头文件的最顶部；源文件最顶部不放任何说明，直接以 `#include` 开头。**
> 文件说明、@details、@note、使用示例等全部收敛到头文件顶部；源文件内只保留函数/分区级注释。

```cpp
/**
 * @file bsp_uart.hpp
 * @author 名字
 * @brief 一句话说明这个文件是干什么的
 * @version 0.2
 * @date 日期
 *
 * @todo 待办事项
 *
 * @copyright Copyright (c) 2026
 *
 * @details 详细说明 / 使用示例
 *
 * @note 注意事项
 */
```

- **函数注释**：`@brief`（必须）+ `@param` + `@return` + `@note`；公共接口必须写全，私有函数可只写 `@brief` 或行注释
- **注释语言**：中文；描述"为什么"，而不是复述代码。要求作为技术人员对代码进行解释，不要过口语化也不要过专业化。
- 未使用的参数写 `(void)arg;` 并注明

### 注释的目标：让人不翻手册就能改对代码

写注释时假设读者是三个月后接手的人：他手上只有这份代码和这颗 MCU 的手册，没有你的记忆。

- **写"为什么"，不写"是什么"**：`slot.limit = 16384;` 要注明 16384 从哪来，而不是再写一遍"给 limit 赋值"
- **把外部资料搬进注释**：从手册 / CubeMX / 上位机截图里查来的值（寄存器值、协议表、引脚、电调 ID），
  必须连来源一起写在旁边，让下一个人能自己核对
- **写"改错了会怎样"**：魔数、字节序、时序、缓冲区长度这些地方，说明误改的后果
- **公式和位运算配一个具体算例**：`last=8000, now=200 → delta = -7800 < -4096 → +8192 = 392` 比一段文字管用
- **交代前置条件**：谁先调、什么状态下才能调、调完之后哪些全局状态会变
- **踩过的坑就地记下来**：为什么不能写成"更自然"的那种写法，免得下一个人再踩一遍

反例 / 正例：

| 反例（复述代码） | 正例（解释原因与来源） |
|---|---|
| `// 把 raw 限幅` | `// 手册给出的原始指令绝对值上限（3508/6020 是 16384，2006 是 10000）` |
| `// 循环 11 次` | `// 从左到右扫一遍 11 个位置，空位跳过` |
| `// 发送数据` | `// 发送结果有意丢弃：失败计数在 BspCan::diagnostics 里查` |
| `// 大端转小端` | `// 手册：反馈帧的多字节字段一律高字节在前` |

必须写注释的位置：

1. 所有对外接口 —— 讲清前置条件、单位、取值范围，而不只是签名
2. 魔数与查表 —— 来源、单位、允许范围
3. 时序与时基 —— 为什么是这个周期 / 阈值，由谁推进
4. 硬件与协议约定 —— 引脚、标识符、字节序、帧布局
5. 非直观的写法 —— 刻意不加锁、刻意少做一步、刻意丢弃返回值
6. 踩过的坑 —— 为什么不能按更自然的写法写

**注释与代码同一次改动更新**：改了行为没改注释，比不写注释更糟。看到过期注释要就地修掉，
不要留给下一个人猜。注释的浓淡按文件职责定：**分层入口文件（`*_cfg`）保持精简**，
**协议 / 算法驱动的 `.hpp` + `.cpp` 要写厚**。

### 分区横幅

源文件与头文件按功能分区，分区用「开始 + 结束」成对的短横线横幅隔开：开始行写分区名，结束行只写短横线。结束行紧贴在下一个分区标题行的上一行，同时充当上一分区的结束与下一分区的开始。

```cpp
// ---------------- 公有接口 ----------------

/** @brief 发送数据（阻塞到写完或超时） */
Status send(const uint8_t *data, size_t size, uint32_t timeout_ms);

// ----------------
// ---------------- ISR 入口 ----------------

extern "C" void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
}

// ----------------
```

- 分区名用中文短语：`构造`、`公有接口`、`ISR 入口`、`私有实现`、`成员变量`
- 类内的分区横幅与类成员保持同级缩进（2 空格），结束行放在类体 `};` 之前
- **分区不可嵌套**：一个文件内所有分区处于同一层级，需要细分就新增同级分区，不要写子分区
- 函数体内不使用横幅，过程说明用普通 `//` 注释

## 4. 断言规范（configASSERT）

`configASSERT` 的定义在 `Core/Inc/FreeRTOSConfig.h`：

```c
#define configASSERT( x ) if ((x) == 0) {taskDISABLE_INTERRUPTS(); for( ;; );}
```

失败即关中断 + 死循环：调试器断下来就能看到是哪一条挂的，现场也不会带着错误状态继续跑。

### 断言写在各对象自己的接口里

**谁有能力判断，谁就断言；外层调用方不重复断言已经断言过的东西。**

```cpp
// ✅ 各层在自己的 init() 里断言，all_init() 直接按顺序调即可
void service_init(void) { configASSERT(sys_state.init() == Status::OK); }
void bsp_init(void)     { configASSERT(bsp_can1.init() == Status::OK); /* ... */ }
void device_init(void)  { configASSERT(can3_dji_group.init() == Status::OK); }

void all_init() { service_init(); bsp_init(); device_init(); }

// ❌ 同一件事断言两遍；而且外层断在笼统的位置，看不出是哪条驱动挂的
void device_init(void) { return can3_dji_group.init(); }
void all_init()        { configASSERT(device_init() == Status::OK); }
```

推论：**一旦接口内部自己断言，它就不可能返回失败，此时返回值应改为 `void`**，
留着 `Status` 返回值等于对外宣称"我会失败"，是骗人的。

### 断言还是返回 Status

判断标准是**这个失败是不是意味着"代码 / 配置写错了"**：

| 情形 | 处理 |
|---|---|
| 初始化失败（句柄为空、RTOS 对象创建失败、外设起不来） | `configASSERT` |
| 编译期就写死的配置与实物不符（电机型号放错位置、通道号填错） | `configASSERT` |
| 自己算出来的下标越界 | `configASSERT` |
| 任务创建失败、`complete_init()` 返回非 OK | `configASSERT`（写在创建/置位处） |
| 运行期收到非法帧、总线忙、超时、缓冲满 | 返回 `Status` |
| 来自外部的输入（上位机报文、按键、传感器）越界 | 返回 `Status` |

```cpp
// ✅ 运行期可恢复的失败 → 返回 Status 交给上层决策
Status DjiMotorGroup::update(const CanRxMsg &rx)
{
  if (!classic_8) { return Status::BAD_ARG; } // 总线上的一帧噪声而已
}

// ❌ 把它断言掉：一帧噪声就能让整车停机
configASSERT(rx.header.DataLength == FDCAN_DLC_BYTES_8);
```

### 其他约定

- **每条断言单独一行**，行尾写清这一条在验什么（如 `// PE9 TIM1_CH1 排针预留（舵机）`），
  这样断点落在哪一行就直接告诉你哪条驱动没起来
- **`configASSERT` 依赖 `FreeRTOS.h`**，用到它的 `.cpp` 显式包含并加 `// IWYU pragma: keep (configASSERT)`
- **本工程 `USE_FULL_ASSERT` 是关闭的**（`Core/Inc/stm32h7xx_hal_conf.h`），HAL 的 `assert_param` 全是空操作，
  所以**驱动的入参校验必须自己写**，不能指望 HAL 替你拦
- **`configASSERT` 不带打印**。需要现场定位时，先把关键值写进 `volatile` 全局变量供调试器查看，再断言；
  测试任务可用 `bsp_uart1.printf()` 补一条人可读的说明
- **中断里尽量不放断言**：关中断 + 死循环在现场只表现为看门狗复位，比直接丢弃一帧更难查；
  ISR 里只做最少校验，非法数据丢掉即可

## 5. 类设计模式

1. **全局实例模式**：在 `xxx_cfg.cpp` 中实例化，`xxx_cfg.hpp` 中 `extern` 声明
2. **模板实例化**：模板类定义在 `.hpp`，显式实例化放 `.cpp`（如 `template class BspUart<64>;`）
3. **HAL 中断回调**：统一放在对应 BSP 的 `.cpp` 中，用 `extern "C"` 包裹，通过句柄查表分发
4. **配置结构体统一模式（Config）**：类的初始化 / 构造参数收进类内的 `Config` 结构体（命名固定为 `Config`）；初始化参数少于三个时直接用裸参数。
5. **构造函数只做赋值**：能在类实现处给默认值的就在那里给，能在构造函数传入的就在构造函数传，不能在构造时完成的放到 `init()`。任何 FreeRTOS 操作或需要运行的调用（`xTaskCreate`、`xSemaphoreCreate*`、`snprintf`、`memset`、注册表注册等）一律移入 `init()`，构造函数中只允许成员赋值。
6. **隐藏逻辑必须显式化**：如 `i_max == 0 → 跟随 out_max`，要写在构造函数里并注释
7. **不使用 `friend`**：需要类外访问的成员与构造函数直接设为 `public`或者写出访问接口，不写友元声明

## 6. 分层架构

依赖方向（上层可用下层，禁止反向）：

```
App（应用层，api_xxx 转接）
 └─ Module
     └─ Device（设备层，单设备驱动）
         └─ Bsp（板载支持包，完全不考虑上层硬件细节）
```

- 跨层通信使用下一层暴露的全局实例，不直接操作 HAL

## 7. C/C++ 混编

### 必须加 `extern "C"` 的场合

- HAL / FreeRTOS 回调必须 `extern "C"`，防止名称修饰
- 任务函数若被 FreeRTOS 以 C 方式调用，需要 `extern "C"` 且参数为 `void *pvParameters`

### 转接的粒度

- C 调 C++ 统一通过 `api_xxx.h` 转接，目前只有 `api_main`（`api_main.h` / `api_main.cpp`）
- C 侧不能直接调用 C++ 类：在 `.c` / `.cpp` 中写 `extern "C"` 转接接口，由 C++ 一侧实现
- 整个工程只在 `main.c` 处转接一次：把 main 的内容提取成 `api_main`，中断回调、初始化、主循环都放入其中；FreeRTOS 同理，加 `extern "C"` 即可。HAL 库自身已提供 C++ 调用 C 所需的 `extern "C"`。

## 8. 书写与格式规则

### 由 .clang-format 固化

- 2 空格缩进、Allman 大括号（换行）
- `*` `&` 靠右：`uint8_t *data`
- 连续赋值 / 声明对齐；行尾注释对齐
- 不限制行长（`ColumnLimit: 0`）
- 指针固定靠右（`DerivePointerAlignment: false`）

格式化为**手动执行**，工程里没有自动格式化：在编辑器中对当前文件执行 Format Document，需要批量统一时直接调用 clang-format（命令与工具来源见 [../guide/clangd配置.md](../guide/clangd配置.md)）。

### 需人工遵守

- 使用 `auto` 能显著提升开发效率或可读性时就用，但必须在旁边写注释说明
