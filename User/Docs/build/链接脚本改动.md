# 链接脚本改动：`.dma_buffer` 段

本文件记录 `STM32H723XG_FLASH.ld` 中自定义段 `.dma_buffer` 的来龙去脉：它为什么存在、原实现
有什么隐患、2026-10-28 为什么改成可加载段、怎么改的、踩了哪些坑、最终结果。

---

## 1. 这个段是干什么的

`.dma_buffer` 存放**必须由 DMA 访问的变量**，本工程里就是各串口驱动实例
（`bsp_uart1` … `bsp_uart10`、`bsp_uart_it5`）。

这些实例内部有三个内嵌数组：

```cpp
uint8_t _rx_buffer[RX_SIZE];       // DMA 接收目标
uint8_t _tx_buffer[TX_SIZE];       // DMA 发送源
char    _printf_buffer[TX_SIZE];
```

对象整体（含这三个数组）必须落在 DMA 能访问的 RAM 里，所以整个对象带段属性：

```c
__attribute__((section(".dma_buffer")))
```

注意：**属性写在对象上，不是写在数组上**。数组是对象的成员，跟着对象走。

---

## 2. 原理

### 2.1 为什么必须放 RAM_D1，不能放 DTCM

STM32H723 的内部 RAM 分域，本工程链接脚本里的定义：

| 区域 | 起始地址 | 大小 | 能否被 DMA1/DMA2 访问 |
|---|---|---|---|
| `DTCMRAM` | `0x2000_0000` | 128 KB | **不能** |
| `RAM_D1`（AXI SRAM） | `0x2400_0000` | 320 KB | 能 |
| `RAM_D2` | `0x3000_0000` | 32 KB | 能 |
| `RAM_D3` | `0x3800_0000` | 16 KB | 能 |

DTCM 是 CPU 的紧耦合存储器，直接挂在 Cortex-M7 内核旁边，**不经过总线矩阵**，
所以 DMA 外设根本看不到它。DMA 去访问 DTCM 地址的结果是传输失败/总线错误。

默认的 `.bss`、`.data` 都落在 `DTCMRAM`（见链接脚本 `} >DTCMRAM`），因此 DMA 缓冲必须显式
挪到 `RAM_D1`。

### 2.2 VMA / LMA / NOLOAD

链接脚本里三个概念必须先分清：

- **VMA**（Virtual Memory Address）：运行时地址。`>RAM_D1` 定的就是这个，本例 `0x2400_0000`。
- **LMA**（Load Memory Address）：初值在映像（flash）里的存放地址。`AT> FLASH` 定的就是这个。
- **`(NOLOAD)`**：声明"这个段没有初始内容"。它**不产生 LMA**，`objcopy` 不把它写进
  `.bin/.hex`，启动代码也不会为它做任何事。

一个段只要带 `AT> FLASH`，就会在 flash 里占一块等长的初值拷贝；带 `(NOLOAD)` 则一块都不占。

### 2.3 启动代码的处理顺序

`startup_stm32h723xx.s` 的 `Reset_Handler` 在跳到 `main()` 之前依次做：

1. 设栈指针 → `ExitRun0Mode()` → `SystemInit()`（配时钟）
2. 把 `.data` 的初值从 flash 拷到 RAM：用 `_sidata` / `_sdata` / `_edata` 三个符号
3. 把 `.bss` 清零：用 `_sbss` / `_ebss`
4. 调 `__libc_init_array()`（跑所有全局构造函数）→ `main()`

**关键点：除了 `.data` 和 `.bss`，没有任何段会被自动处理。**
链接脚本里新加的段若想让它在启动时"有内容"，必须自己在 `Reset_Handler` 里加代码。

### 2.4 C++ 全局对象的两种初始化

同一个 `bsp_uart1`，按类的构造方式不同，走的路完全不同：

| | 常量初始化（constant initialization） | 动态初始化（dynamic initialization） |
|---|---|---|
| 触发条件 | 构造函数 `constexpr`，且初值全是编译期常量 | 构造函数非 `constexpr`，或初值需要运行时计算 |
| 初值存放 | 直接写进目标段的映像（需要 LMA） | 不存初值，改存"要调用哪个构造函数" |
| 启动时动作 | 无（拷贝段就够了） | 由 `.init_array` 表，`__libc_init_array()` 逐个调用 |
| 对段的要求 | **必须可加载**（有 LMA） | 只要段能被写就行（NOLOAD 也可以） |

这就是整个问题的根源：
**在 `(NOLOAD)` 段里，只有"动态初始化"能正常工作，"常量初始化"的初值会静默丢失。**

## 3. 改动前的问题

### 3.1 改动前的形态（原始快照）

下面是 2026-10-28 之前的写法，中文注释之间为当初添加的内容，前后未变的部分用于定位：

```c
  .fini_array (READONLY) : /* The "READONLY" keyword is only supported in GCC11 and later, remove it if using GCC10 or earlier. */
  {
    . = ALIGN(4);
    PROVIDE_HIDDEN (__fini_array_start = .);
    KEEP (*(SORT(.fini_array.*)))
    KEEP (*(.fini_array*))
    PROVIDE_HIDDEN (__fini_array_end = .);
    . = ALIGN(4);
  } >FLASH

 /* === 用户为dma传输配置的内存地址 === */

  .dma_buffer (NOLOAD) :
  {
    . = ALIGN(32);
    _sdma_buffer = .;
    *(.dma_buffer)
    *(.dma_buffer*)
    . = ALIGN(32);
    _edma_buffer = .;
  } >RAM_D1

  /* === 用户dma相关配置结束 === */

  /* used by the startup to initialize data */
  _sidata = LOADADDR(.data);

  /* Initialized data sections goes into RAM, load LMA copy after code */
  .data :
  {
    . = ALIGN(4);
    _sdata = .;        /* create a global symbol at data start */
    *(.data)           /* .data sections */
    *(.data*)          /* .data* sections */
    *(.RamFunc)        /* .RamFunc sections */
    *(.RamFunc*)       /* .RamFunc* sections */

    . = ALIGN(4);
  } >DTCMRAM AT> FLASH
```

### 3.2 它为什么"以前能用"

改动前 `BspUartT` 的构造函数是普通函数（只做三个成员赋值），对象走**动态初始化**：
`.init_array` 里登记了构造函数，`__libc_init_array()` 启动时把它跑一遍，把 `_huart`、`_mode`、
`_baudrate` 和一堆 `nullptr` 写进 RAM。

`(NOLOAD)` 只要求"段可写"就够了，所以这条路是通的 —— 但**依赖一个隐式前提：构造函数永远非 `constexpr`**。

### 3.3 隐患：三个只要发生一个就静默失效

| 触发条件 | 例子 | 后果 |
|---|---|---|
| 给成员加非零默认值 | `UartMode mode = UartMode::TxRx;` | 该字段是上电残留值 |
| 构造函数改成 `constexpr` | 为了让 `inline` 全局实例常量初始化 | 整个对象是上电残留值 |
| 改用聚合体 + 指定初始化器 | `Config` 聚合化后一次性构造 | 同上 |

失效时的表现不是崩溃、不是断言，而是**字段变成随机值**：

- `_huart` 变成野指针 → 首次 `HAL_*` 调用直接 HardFault，或写坏外设寄存器；
- `_tx_stream_buffer` / `_tx_lock` 变成非空野值 → `init()` 里的"是否已创建"判断失效；
- 状态机初值随机 → 行为不可复现。

而且**编译、链接全程没有任何警告** —— 这类问题只能靠翻链接脚本才查得到。

## 4. 方案对比与选型

| 方案 | 做法 | 常量初始化是否正确 | flash 代价 | 备注 |
|---|---|---|---|---|
| **A** 保持 `NOLOAD`，只靠"构造函数一定非 constexpr" | 不动 | ❌ 隐式丢失 | 0 | 无法用编译器强制，只能靠人记 |
| **B** 保持 `NOLOAD`，启动时把该段清零 | 加一段清零循环 | 只对"初值全 0"成立 | 0 | 非零初值仍然丢 |
| **C** 改成可加载段，启动时拷贝 | 本文采用 | ✅ 都正确 | +段大小（全 0，3648 B） | 一次解决，代价明确 |

选 **C**。理由：

1. 只有 C 能让"常量初始化 / 动态初始化"两种方式**都**正确，不再依赖任何约定；
2. 代价可控：`.dma_buffer` 里全是 0（缓冲区 + 指针初值），这部分 flash 纯粹是 0 填充，
   1 MB flash 当前只用到 14.6%；
3. 方案 B 看着更省，但它把"能不能加非零默认值"这条限制永久固化下来了，和"类内 NSDMI
   写默认值"的代码风格直接冲突。

## 5. 具体改动（过程）

### 5.1 链接脚本 `STM32H723XG_FLASH.ld`

> ⚠ 本工程有**两个**链接脚本：`STM32H723XG_FLASH.ld`（大写 XG，**构建实际使用**）与
> `STM32H723xG_flash.ld`（小写，旧副本，没有 `.dma_buffer`）。改错文件不会生效。
> 确认方法：`build/Debug/build.ninja` 里 `-T` 后面跟的那个。

改前 → 改后：

```c
-  .dma_buffer (NOLOAD) :
+  .dma_buffer :
   {
     . = ALIGN(32);
     _sdma_buffer = .;
     *(.dma_buffer)
     *(.dma_buffer*)
     . = ALIGN(32);
     _edma_buffer = .;
-  } >RAM_D1
+  } >RAM_D1 AT> FLASH
+  _sidma_buffer = LOADADDR(.dma_buffer);
```

三处改动各自的作用：

| 改动 | 作用 |
|---|---|
| 删掉 `(NOLOAD)` | 让该段产生 LMA（初值落进 flash 映像） |
| 加 `AT> FLASH` | 显式指定 LMA 在 FLASH 区；`objcopy` 会把初值写进 `.bin/.hex` |
| 加 `_sidma_buffer` | 把 LMA 起点导出成符号，供启动代码使用 |

`ALIGN(32)` 保留不动：DMA 缓冲按 32 字节（cache line）对齐，即使现在 D-Cache 没开，
将来开启后也不会因为跨行导致一致性问题。

### 5.2 启动文件 `startup_stm32h723xx.s`

在 `.data` 拷贝循环之后、`.bss` 清零之前插入第二段拷贝：

```asm
  ldr   sp, =_estack
  bl    ExitRun0Mode
  bl    SystemInit

  /* —— 原有的 .data 拷贝 —— */
  ldr r0, =_sdata
  ldr r1, =_edata
  ldr r2, =_sidata
  ...

/* —— 新增：把 .dma_buffer 的初值从 flash 拷到 RAM_D1 —— */
  ldr r0, =_sdma_buffer
  ldr r1, =_edma_buffer
  ldr r2, =_sidma_buffer
  movs r3, #0
  b LoopCopyDmaBufferInit

CopyDmaBufferInit:
  ldr r4, [r2, r3]
  str r4, [r0, r3]
  adds r3, r3, #4

LoopCopyDmaBufferInit:
  adds r4, r0, r3
  cmp r4, r1
  bcc CopyDmaBufferInit

/* —— 原有的 .bss 清零 —— */
  ldr r2, =_sbss
  ...

  bl __libc_init_array
```

为什么必须单独一段循环、不能并进 `.data` 的循环：

- `.data` 的目标区间是 `[_sdata, _edata)`，在 `DTCMRAM`（`0x2000_0000`）；
- `.dma_buffer` 的目标区间是 `[_sdma_buffer, _edma_buffer)`，在 `RAM_D1`（`0x2400_0000`）；
- 两者**不相邻、中间隔着整个地址空间**，用一次连续拷贝覆盖不了。

顺序要求：必须放在 `__libc_init_array()` **之前**，否则常量初始化的对象在构造函数跑之前
就是"未被装载"的状态。

### 5.3 验证方法（三步）

```bash
# ① 段的 VMA / LMA：LMA 必须在 flash（0x08xxxxxx），且带 LOAD 标志
arm-none-eabi-objdump -h build/Debug/DM_MC02.elf | grep -A1 dma_buffer
#   8 .dma_buffer  00000e40  24000000  080242f4  00026000  2**2
#                  CONTENTS, ALLOC, LOAD, DATA
#                            ^VMA     ^LMA

# ② 三个边界符号：_sidata 应等于 _sidma_buffer + 段大小
arm-none-eabi-nm build/Debug/DM_MC02.elf | grep -E "_sidma_buffer|_sdma_buffer|_edma_buffer"
#   24000e40 D _edma_buffer
#   24000000 D _sdma_buffer
#   080242f4 A _sidma_buffer
#   （0x080242f4 + 0xe40 = 0x08025134 = _sidata ✓）

# ③ 反汇编确认拷贝循环位置：在 .data 拷贝之后、__libc_init_array 之前
arm-none-eabi-objdump -d --no-show-raw-insn build/Debug/DM_MC02.elf \
  | sed -n '/<Reset_Handler>:/,/__libc_init_array/p'
```

## 6. 过程中踩到的两个坑

### 6.1 `inline` 实例不能共用同一个段名 → 实例被静默丢掉

改成可加载段之后，`bsp_cfg.hpp` 里的实例同时改成了 C++17 `inline` 变量。**每个包含该头文件的
TU 都会 emit 一份弱定义**。若全部写 `section(".dma_buffer")`，多个 TU 会产生**同名段内容不同**
（各自只包含本 TU 用到的那些实例），链接器 + `--gc-sections` 的结果是丢掉一部分：

```text
实测：9 路串口只剩 2 路
  RAM_D1: 3648 B → 928 B
  nm 里 bsp_uart3 ~ bsp_uart10 直接消失
  编译、链接、运行均无任何报错
```

正确写法：**每个变量用唯一段名**，链接脚本的 `*(.dma_buffer*)` 通配仍能收拢：

```c
inline __attribute__((section(".dma_buffer.bsp_uart1"))) BspUartT<...> bsp_uart1({...});
```

### 6.2 `inline` 实例走动态初始化 → 每个 TU 生成一份初始化代码

如果对象不是常量初始化，GCC 会在**每个 odr-use 它的 TU** 里生成
`__static_initialization_and_destruction_0` 及配套 guard：

```text
实测：每个这样的初始化函数约 1.7 KB（0x6c0）
  FLASH: 155544 B → 179188 B（+23.6 KB，仅此一项）
```

解决办法是让对象变成**常量初始化**，条件有两条：

1. 构造函数 `constexpr` 且**定义在头文件里**；
2. **析构函数必须平凡**（`~X() = default`）—— 一旦用户提供析构函数，类型就不是字面类型，
   仍会退回动态初始化并注册 `atexit`。

因此 `BspUartT` / `BspCanT` 的析构改成了 `= default`，原来的清理逻辑挪到显式的
`deinit()`（全局实例永不析构，语义不变）。

改完后：初始化符号总计 **72 B**。

## 7. 结果（实测）

段布局：

| 段 | VMA | LMA | 大小 | 标志 |
|---|---|---|---|---|
| `.dma_buffer` | `0x2400_0000` | `0x0802_42f4` | 3648 B | CONTENTS / ALLOC / **LOAD** / DATA |
| `.data` | `0x2000_0000` | `0x0802_5134` | 1252 B | CONTENTS / ALLOC / LOAD / DATA |
| `.bss` | `0x2000_04e8` | — | 61780 B | ALLOC |

关键符号：

| 符号 | 值 | 含义 |
|---|---|---|
| `_sdma_buffer` | `0x2400_0000` | RAM_D1 里的起始地址（`_sdata` 之前的独立区间） |
| `_edma_buffer` | `0x2400_0e40` | 结束地址 |
| `_sidma_buffer` | `0x0802_42f4` | flash 里的初值起点 |

内存占用（Debug，`-O0`）：

```text
DTCMRAM:  67136 B (51.22%)   ← 与改动前一致
RAM_D1:    3648 B (1.11%)    ← 与改动前一致（只是现在 flash 也占同样大小）
FLASH:   153112 B (14.60%)   ← 相比 NOLOAD 版多出 3648 B
```

**净结果**：多花 3648 B flash（内容全 0），换来"无论常量初始化还是动态初始化都正确"，
且这套结构不再依赖任何隐式约定。

## 8. 回归检查清单

以后任何人动 `bsp_cfg.hpp` 的实例、`BspUartT` 的构造函数，或链接脚本，都要过一遍：

- [ ] `objdump -h` 里 `.dma_buffer` 有 **LOAD** 标志，LMA 在 `0x08xxxxxx`
- [ ] `_sidma_buffer + 段大小 == _sidata`（说明两段 LMA 首尾相接、没有重叠）
- [ ] 反汇编 `Reset_Handler`，`CopyDmaBufferInit` 循环在 `__libc_init_array` 之前
- [ ] `nm` 里实例个数与 `bsp_cfg.hpp` 定义的数量一致（尤其串口 9 路）
- [ ] 所有 `.dma_buffer` 实例的段名**按变量唯一**（`.dma_buffer.<变量名>`）
- [ ] `sizeof` / 地址与改动前一致（`bsp_uart*` 应在 `0x2400_0xxx`）
- [ ] 内存报告三栏（DTCMRAM / RAM_D1 / FLASH）与改动前对齐，flash 增量等于 `.dma_buffer` 大小
